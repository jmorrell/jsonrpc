# Bidirectional RPC Design

## Summary

This design makes two changes to the JSON-RPC library. First, it removes the notification concept entirely: the client proxy loses its `.notify` method, and `RpcClient<T>` becomes a plain `PromisifyMethods<T>`. Every call is now a method call that waits for a response. The server side detects incoming notifications from third-party clients and ignores them rather than executing their handlers, logging a warning through the existing `onError` callback.

Second, it adds a symmetric `rpcSession()` primitive that enables bidirectional RPC over a message-oriented transport (such as a WebSocket). Both sides of a connection use the same `rpcSession()` function and each gets a `remote` proxy to call methods on the other side. The only asymmetry is ID generation: the initiator uses positive integers and the acceptor uses negative integers, preventing collisions when both sides call each other simultaneously. To support this cleanly, shared runtime code (`processRpc`, `RpcError`, request/response builders, type guards) is first consolidated into a new `core.ts` module, making `client.ts`, `server.ts`, and the new `session.ts` thin layers with no cross-imports. No concrete transport implementations are shipped as part of this work.

## Definition of Done

1. **Notifications removed**: `.notify` proxy removed from client, `RpcClient` type simplified to just `PromisifyMethods<T>`, server ignores (does not execute) incoming notifications and logs a warning via `onError`, all notification-related tests updated or removed.

2. **Bidirectional RPC core**: A symmetric session primitive where both sides can call methods on each other over a message-oriented transport. Includes:
   - `RpcMessageTransport` interface (send/onMessage/onClose/close)
   - `rpcSession()` — symmetric entry point used by both sides (takes transport + service + role, returns session with `remote` proxy)
   - `rpcClient()` unchanged (HTTP-only, not overloaded)
   - ID collision avoidance (initiator uses positive IDs, acceptor uses negative IDs)
   - All pending promises reject with the transport error on disconnect

3. **No transport implementations**: `RpcMessageTransport` interface is defined but no concrete transports (e.g., `websocketTransport()`) are shipped. An in-memory test transport is sufficient for testing.

4. **Out of scope**: Reconnection, per-call timeouts, backpressure, SSE, transport implementations.

## Acceptance Criteria

### bidi-rpc.AC1: Notifications removed
- **bidi-rpc.AC1.1 Success:** Client proxy has no `.notify` property — accessing it returns `undefined`
- **bidi-rpc.AC1.2 Success:** `RpcClient<T>` type is equivalent to `PromisifyMethods<T>` (no notify member)
- **bidi-rpc.AC1.3 Success:** Void-returning methods return `Promise<void>` that resolves when the server processes the call (response has `result: null`)
- **bidi-rpc.AC1.4 Success:** Server detects incoming notification (`!("id" in body)`) and returns `null` without executing the method handler
- **bidi-rpc.AC1.5 Success:** Server logs incoming notification via `onError` callback
- **bidi-rpc.AC1.6 Edge:** Batch containing mix of requests and notifications: requests produce responses, notifications are ignored, notification handlers are not executed

### bidi-rpc.AC2: Bidirectional RPC session
- **bidi-rpc.AC2.1 Success:** Initiator can call methods on acceptor's service via `session.remote`
- **bidi-rpc.AC2.2 Success:** Acceptor can call methods on initiator's service via `session.remote`
- **bidi-rpc.AC2.3 Success:** Both sides can call each other simultaneously without ID collision (initiator uses positive IDs, acceptor uses negative IDs)
- **bidi-rpc.AC2.4 Success:** Void-returning remote methods resolve `Promise<void>` when processed
- **bidi-rpc.AC2.5 Success:** Remote method that throws returns `RpcError` to the caller with code, message, and optional data
- **bidi-rpc.AC2.6 Failure:** Calling a method that doesn't exist on the remote service rejects with -32601 Method not found
- **bidi-rpc.AC2.7 Success:** Messages are sent individually (no batching over message transport)

### bidi-rpc.AC3: Connection lifecycle
- **bidi-rpc.AC3.1 Success:** When transport closes, all pending outgoing calls reject with the close reason
- **bidi-rpc.AC3.2 Success:** `session.close()` calls `transport.close()` and rejects pending calls
- **bidi-rpc.AC3.3 Failure:** Calling `session.remote.method()` after close rejects immediately
- **bidi-rpc.AC3.4 Edge:** Transport closes while a service method is executing — response send is attempted but failure doesn't crash

### bidi-rpc.AC4: Error resilience
- **bidi-rpc.AC4.1 Success:** Malformed JSON on transport is logged via `onError` and ignored — session stays alive
- **bidi-rpc.AC4.2 Success:** Response with unknown ID is logged via `onError` and ignored
- **bidi-rpc.AC4.3 Success:** Message that is neither request nor response is logged via `onError` and ignored
- **bidi-rpc.AC4.4 Success:** `transport.send()` throwing rejects only the specific call, not the whole session
- **bidi-rpc.AC4.5 Success:** Incoming notification on session is ignored (not executed), logged via `onError`

## Glossary

- **JSON-RPC 2.0**: A stateless, transport-agnostic remote procedure call protocol encoded in JSON. Each call is a `{ jsonrpc, method, params, id }` object; the response is `{ jsonrpc, result|error, id }`.
- **Notification**: A JSON-RPC request with no `id` field. The sender does not expect a response. This library removes its use of notifications so every call is a trackable method call.
- **Bidirectional RPC**: A pattern where both endpoints of a connection can initiate method calls on each other, rather than one side being a fixed client and the other a fixed server.
- **Initiator / Acceptor**: The two roles a session participant can take. The initiator opens the connection (positive IDs); the acceptor receives it (negative IDs). Used only for ID range assignment.
- **`RpcMessageTransport`**: A four-method interface (`send`, `onMessage`, `onClose`, `close`) abstracting any message-oriented channel over which individual JSON-RPC messages are exchanged.
- **`processRpc()`**: An existing internal function that handles JSON-RPC dispatch — parsing an incoming request, calling the appropriate method on the service object, and building a response. Reused unchanged by the session for incoming requests.
- **`PromisifyMethods<T>`**: A TypeScript utility type that takes a service interface and returns a version where every method returns a `Promise`. Used as the type of the `remote` proxy.
- **Pending-call tracking**: The client-side bookkeeping pattern — a `Map<id, {resolve, reject}>` — that stores in-flight outgoing calls so incoming responses can be matched back to the correct `Promise`.
- **ID collision avoidance**: The mechanism by which both sides generate request IDs concurrently without duplicates. Initiator uses positive IDs (1, 2, 3, ...), acceptor uses negative IDs (-1, -2, -3, ...).
- **capnweb**: The prior-art library this design cites for the ID polarity scheme and symmetric session model.
- **Message-oriented transport**: A channel that delivers discrete, framed messages rather than a raw byte stream. Each `send` produces exactly one `onMessage` on the other side.

## Architecture

Two changes to the library: remove notifications (simplify), add bidirectional sessions (extend).

**Notification removal.** The `.notify` proxy and all notification-related code are removed from the client. `RpcClient<T>` becomes `PromisifyMethods<T>`. On the server, incoming notifications are detected and ignored (not executed) — a warning is logged via `onError`. Every call is a method call; void-returning methods return `{ result: null }`.

**Bidirectional sessions.** A new symmetric `rpcSession()` primitive. Both sides of a connection use the same function — the only configuration difference is `role` (`'initiator'` or `'acceptor'`), which determines ID polarity. Each session runs client logic (outgoing calls via proxy, pending-call tracking) and server logic (incoming request dispatch via `processRpc`) simultaneously.

**Module refactoring.** Shared runtime code (type guards, request/response builders, `RpcError`, `processRpc`) is extracted into `core.ts`. The leaf modules (`client.ts`, `server.ts`, `session.ts`) are thin layers over `core.ts` with no cross-imports.

### Contracts

```typescript
// Transport for message-oriented connections
type RpcMessageTransport = {
  send(message: string): void;
  onMessage(handler: (message: string) => void): void;
  onClose(handler: (reason?: Error) => void): void;
  close(): void;
};

// Session entry point — symmetric, used by both sides
function rpcSession<TRemote extends object, TLocal extends object>(
  transport: RpcMessageTransport,
  service: TLocal,
  options?: RpcSessionOptions,
): RpcSession<TRemote, TLocal>;

type RpcSessionOptions = {
  role?: 'initiator' | 'acceptor';  // default: 'initiator'
  onError?: (err: unknown) => void;
};

type RpcSession<TRemote extends object, TLocal extends object> = {
  remote: PromisifyMethods<TRemote>;
  close(): void;
};
```

### Message routing

When a message arrives on the transport, the session parses it and routes:

- Has `method` field → **incoming request** → dispatch via `processRpc(parsed, service)`, send response back via `transport.send()`
- Has `result` or `error` field → **incoming response** → match to pending call by `id`, resolve/reject the promise
- Neither → log via `onError`, ignore

No batch support over message transports. Each message is a single JSON-RPC request or response.

### ID collision avoidance

Both sides generate request IDs from separate ranges:

- **Initiator**: positive integers, incrementing from 1 (1, 2, 3, ...)
- **Acceptor**: negative integers, decrementing from -1 (-1, -2, -3, ...)

Borrowed from capnweb's split-namespace approach.

### Connection lifecycle

On transport close (`onClose` fires):
- All pending outgoing calls reject with the close reason (or generic "connection closed" error)
- Pending call map is cleared

On `session.close()`:
- Calls `transport.close()`
- Same pending-call cleanup

### Error handling

All errors route through `onError` — nothing is silently swallowed.

| Scenario | Behavior |
|----------|----------|
| Response for unknown ID | Log via `onError`, ignore |
| Malformed JSON | Log via `onError`, ignore (session stays alive) |
| `transport.send()` throws | Reject the specific outgoing call's promise |
| Service method throws | `processRpc` catches it, sends error response back |
| Unroutable message | Log via `onError`, ignore |
| Incoming notification | Ignore (don't execute), log via `onError` |

## Existing Patterns

Investigation found that the library already has clean separation between transport-agnostic logic and HTTP-specific wrappers:

- `processRpc()` handles all JSON-RPC dispatch without HTTP assumptions. The session reuses this directly for incoming request handling.
- The client's pending-call tracking pattern (`Map<id, {resolve, reject}>`, match responses by ID) is replicated in the session for outgoing calls, adapted for immediate send (no `setTimeout(0)` batching).
- `createRequest()`, `isJsonRpcResponse()`, `isJsonRpcRequest()`, `RpcError`, and response builders are shared primitives used by both the HTTP client and the bidirectional session. Currently split between `client.ts` and `server.ts` — this design consolidates them in `core.ts`.
- In-memory test transport pattern from `e2e.test.ts` (pipe client transport directly into `processRpc`) informs the `createLinkedTransports()` test helper for bidirectional testing.

No divergence from existing patterns. The session follows the same dispatch and error-handling conventions.

## Additional Considerations

**Batching is transport-coupled.** HTTP clients batch via `setTimeout(0)` because round-trips are expensive. Message transports send immediately because messages are cheap. This falls out naturally from the two transport types — no configuration needed.

**Notifications as a spec deviation.** JSON-RPC 2.0 defines notifications; this library chooses not to use them. The server still detects notifications (for third-party client compatibility) but does not execute them. This is documented behavior, not a bug.
